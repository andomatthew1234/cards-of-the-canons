# Firestore account-security audit

Scope: the account-security centre additions targeting the existing Standard edition `(default)` database in `australia-southeast1`.

## Paths and operations

- `usersPrivate/{uid}` remains owner/admin readable and schema-validated for owner writes.
- `orders/{id}` remains owner/admin read-only; no account-setting flow writes orders.
- `accountSecurity/{uid}` is a server-owned policy document. Web clients perform no direct reads or writes; an authenticated, App-Check-protected callable sanitises the returned structure.
- `_securityChallenges/{id}` is reserved for future hashed, expiring challenge records and is denied to every web client.
- `_abuseCounters/{id}` remains server-only for future challenge throttling.

## Red-team checks

- Public list/get: denied for both new collections.
- Cross-user access: denied because all client access is denied, including owners and administrators.
- Update bypass/schema pollution: denied because clients cannot create or update either collection.
- Ownership hijacking: no client-owned identity field exists in the new paths.
- Privilege escalation: security policy cannot create or alter administrator custom claims.
- Plaintext-code disclosure: no client-readable challenge path exists and no email code is generated by the current implementation.
- Query mismatch: the web app uses an authenticated callable, not a Firestore query, for policy retrieval.
- Resource exhaustion: web-client writes are denied; future Functions must validate bounded policy/challenge schemas before server writes.

The existing broader ruleset should continue to be reviewed before a large public launch. These additions intentionally preserve default-deny and least-privilege behaviour.
